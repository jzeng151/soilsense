# Data freshness policy

Provider documentation checked live on 2026-11-15. Sampling resolution is **not** publication cadence. “Historical” means stable enough for a long cache, not a claim that a provider can never reprocess it. Source payload/QA/parsing and plan calculations are unchanged.

## Implemented policy

All migrated source keys begin `fresh-v1:` in addition to their existing payload/product version and requested years. Bump `FRESHNESS_VERSION` when cache semantics or serialization changes; bump the product version for a new collection. No D1 migration or new binding is needed. Existing entries age out without a destructive cache purge.

## Stale-while-revalidate and safety

`cached` accepts either a numeric hard TTL (backward compatible) or `{ softTtlSeconds, staleSeconds, cacheable? }`. D1 `expires_at` is the hard limit; the soft boundary is hard expiry minus stale allowance. Thus recomputing a release-relative TTL on a later read does not shorten/extend an existing entry. No payload envelope is added.

Hono request middleware scopes the actual request's execution context with `AsyncLocalStorage`. A soft-expired source value is returned immediately and a bounded source download/write is registered with **that request's** `ctx.waitUntil`. No module-global context leaks between requests. Cold/hard-expired loads block; callers without an execution context also block on refresh. Concurrent loads/refreshes for the same key share an isolate-local promise. This is **not** a distributed D1 lease; multiple isolates can refresh independently. Refresh errors preserve the previous accepted data until its original hard expiry and suppress repeat refresh attempts for 60 seconds. They never refresh its age. Source fallback values can opt out of storage using `cacheable`.

Numeric finished-plan caching remains hard-expiry only. SWR does **not** run the planner in the background, does not remove Workers Free's 10 ms CPU limit, and does not replace `PLAN_COMPUTE_MODE=cache-only` / demo prewarming. Existing per-source retry/timeouts still bound network work. Parsing historical data still consumes CPU; cache hits are not a claim that every uncached plan fits Workers Free.

## POWER revision sweep

The existing daily 05:43 UTC Workflow is unchanged for the 60-day current-observation stream and Field Watch rules. On Sundays the Workflow additionally rechecks **90 requested days per distinct watched grid cell** in retried steps. Full validated raw revision responses are stored for one year under a separate versioned `power-revisions` archive key, with requested dates and retrieval time. Failed/invalid results do not replace accepted data. These revision archives are evidence, **not new rule inputs**; historical climate requests refresh overlapping years independently via their daily source cache. No second cron or binding is introduced.
